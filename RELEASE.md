# Release Guide

Release reference for coordinated workspace releases.

## Stability Matrix

| Crate | Status | Release Expectation | Notes |
|-------|--------|---------------------|-------|
| `solverforge-core` | Stable | Publish on every coordinated release | Foundational score/domain traits; lowest-level dependency |
| `solverforge-macros` | Stable | Publish on every coordinated release | Proc-macro surface used by the facade and templates |
| `solverforge-scoring` | Stable | Publish on every coordinated release | Constraint-stream and incremental scoring engine |
| `solverforge-config` | Stable | Publish on every coordinated release | Runtime configuration consumed by the solver layer |
| `solverforge-solver` | Stable | Publish on every coordinated release | Main solve engine and manager APIs |
| `solverforge-bridge` | Beta | Publish on every coordinated release | Dynamic host-language binding contracts that depend on config, core, scoring, and solver |
| `solverforge` | Stable | Publish on every coordinated release | Public facade crate and primary library entry point |
| `solverforge-cvrp` | Beta | Publish on every facade version change | Required by the facade's exact-version dependency set |
| `solverforge-console` | Beta | Publish on every facade version change | Required for the facade's exact-version optional `console` feature |

Status definitions:

- `Stable`: public API expected to remain coherent across the release line; regressions block release.
- `Beta`: supported and versioned, but still more likely to receive usability and coverage fixes between patch releases.

## Release Pipeline

Pushing a `v*` tag starts `.github/workflows/release.yml`, the only path to
crates.io and GitHub Releases:

1. `CI` runs the full cross-platform CI (`ci.yml`, Linux, macOS, Windows, and
   the integration and doc tests) on the tagged commit with the toolchain
   pinned in `rust-toolchain.toml`.
2. `Verify release` requires the tag to equal `v` plus the workspace version
   and packages every publishable crate against a local registry overlay.
3. `Publish to crates.io` uploads the publishable crates that are not yet on
   crates.io at that version. Cargo orders them by their dependencies and waits
   for each to reach the index; a re-run uploads only what is still missing.
   The job then confirms that every crate is on crates.io.
4. `Create GitHub Release` creates the release with generated notes.

Each job needs the previous one, so a red CI leg, a tag that does not match
the workspace version, or a crate that fails to package publishes nothing and
creates no release. Running the workflow manually (`workflow_dispatch`)
rehearses steps 1 and 2 on the selected ref without publishing.

CI and the release use the exact toolchain in `rust-toolchain.toml`. Bump it
deliberately, in its own commit, after the workspace passes on the new version.

## Release Checklist

1. Confirm the release branch is correct.
   Use the current release branch or `main` according to the active release plan.
2. Confirm all release-blocking PRs are merged.
   Verify open issues/PRs targeted at the release branch are either merged or explicitly deferred.
3. Sync version and changelog state.
   Run `csemver --dry-run` to preview the release (add `--release-as <level>`
   when the conventional bump needs an override), then run it without
   `--dry-run` after qualification. csemver updates the workspace version and
   publish-time dependency versions, regenerates `Cargo.lock` and
   `docs/architecture.html` through its `postbump` script, and updates the
   README, `AGENTS.md`, and every crate wireframe through its native regex
   updaters (all configured in `csemver.toml`). It generates `CHANGELOG.md`;
   do not hand-edit routine release notes. `make pre-release` runs
   `scripts/release/check-changelog.py` on the dry run first: it fails when the
   new section's version already has a CHANGELOG heading, when its compare link
   is not an absolute GitHub URL, when the link starts from a version with no
   `v` tag or one that is not older, and when the new tag already exists
   locally or on GitHub. Re-run validation on the generated release commit
   before pushing its branch and tag.
   GitHub Release notes are generated by the release workflow from merged PR metadata; do not hand-write routine contributor credits in the release body.
4. Validate canonical docs.
   Check `README.md`, all crate `WIREFRAME.md` files, crate READMEs, focused
   extension guides, Rust API documentation, and this document for stale
   public-surface details. Update the architecture SVG source and regenerate
   `docs/architecture.html`; version-only releases regenerate it automatically.
5. Run formatting and lint gates.
   `cargo fmt --all -- --check`
   `cargo clippy --workspace --all-targets --all-features -- -D warnings`
6. Run test gates.
   `cargo test --workspace --all-features`
   `make pre-release`
7. Run the controlled-host zero-regression qualification.
   On a dedicated Linux host with `taskset`, `/usr/bin/time`, readable `/sys`
   CPU topology, CPU 10 available by default, passwordless `sudo` (the gate
   isolates the measured CPU and its siblings in a cgroup cpuset partition
   while trials run), and optional unprivileged `perf` counters, run:
   `BENCH_CPU=10 WARMUPS=5 TRIALS=51 make bench-zero-regression`
   For an apples-to-apples comparison against a baseline that already uses the
   cursor-owned construction API, set
   `BASELINE=<commit> BASELINE_CURSOR_API=1`; the default historical baseline
   keeps `BASELINE_CURSOR_API=0` for its former eager construction harness.
   For a baseline from an older API generation whose bench sources no longer
   compile against it, set `BENCH_OWN_SOURCES=1`: each side then compiles its
   own tree's gate sources, the comparator relaxes semantic matching to exact
   candidate counts, and any `scripts/bench/*-fixup.patch` files are applied
   to the baseline tree before harness compilation (they repair benches that
   an API cleanup broke before the regular build started compiling them).
   The gate requires exact equality for the deterministic allocation counters
   and grades noisy wall-time and hardware-counter medians against the
   documented `BENCH_TOLERANCE_PERCENT` median regression budget (5% by
   default). This is a separate required release qualification. It is
   intentionally not part of portable `make pre-release`; inability to run it
   is not a pass.
8. Verify publishability.
   `make publish-crates-dry` packages every publishable crate the way the
   release pipeline does.
9. Push the release commit, then its tag.
   Pushing the tag starts the release pipeline described above; it is the only
   way crates reach crates.io. If it fails, fix the cause on `main` and cut a
   new version. If only the upload or release step failed for an external
   reason (crates.io or GitHub outage), re-run the failed jobs of the same run.
10. Post-publish verification.
    Confirm crates.io versions, docs.rs builds, and install smoke tests:
    `cargo add solverforge@<version>`

`solverforge-cli` now releases from its standalone repository and should be validated and published there.

## Release Notes Inputs

Capture these before tagging if the release needs manual emphasis beyond the generated notes:

- Breaking public-surface changes, if any
- New templates, commands, macros, or helper APIs
- New validation coverage or release-risk reductions

The published GitHub Release body is generated automatically from merged PRs and contributor mentions. Only add manual release-note text when users need extra migration or rollout guidance that the generated notes would not communicate clearly.
